# AZ-019 host owner-lock integration feasibility review

Read-only review; no source/Cargo/ledger changes, builds or subprocess fixture executions. Current ManagedRun creates Queued before waiting for slots in chat_send, then start_bound changes Running in chat_turn. finish/Drop persist terminal state; queued guard is dropped before TaskRegistration release. Headless/heartbeat reaches begin_bound without a prequeued guard. TaskActivity and environment_access are process-local and do not prove another desktop process is gone. Current Run rows contain no durable owner epoch, and RecoveryStore accepts an explicit trusted OwnerEvidence assertion; it cannot manufacture that assertion from startup, PID, clock age or active state.

Dependency findings: no fs2/fs4/fd-lock package was found in the checked lockfile/manifests. Local rustc is1.99.0 but desktop Cargo declares rust-version1.77.2. Rust standard File::try_lock is available only since1.89, so using it requires an explicit supported-toolchain change or a separately approved compatible lock dependency/platform adapter. Transitive windows-sys/libc presence is not a direct dependency contract. The official File documentation also makes lock lifetime depend on all duplicate/inherited handles; use distinct non-inherited handles and do not clone a guard. [Rust File locking contract](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock).

Minimal viable design: a stable canonical-project + task lock file, e.g. .agentz/execution-owners/<SHA256(taskID)>.lock, owned by a RAII exclusive OS lock. Never unlink, replace or truncate this lock file during normal life or recovery: Unix unlink can create two independently locked inodes, and Windows open-file deletion/rename rules must not be used as liveness proof. Open read/write, nonappend; refuse unexpected symlink/reparse/path alias according to an explicit trusted-project policy. Lock contention is Alive/Busy; missing historical owner metadata, unsupported filesystem or I/O/lock errors are Unverifiable, not Gone. File existence is not ownership. Scope initially supported local filesystems; network/remote ownership remains unsupported until lock guarantees are proven.

Persist a separate versioned owner namespace in runs.db, indexed uniquely by run/attempt and carrying canonical task/environment, generated host owner epoch and stable lock identity. Queue creation + owner attachment must be one Immediate transaction; cannot safely commit Queued and attach ownership in a later independent commit, since a crash then leaves an unproven owner. Old Runs without owner records remain Unverifiable. Read-only inspection never initializes this namespace. An explicit write initializer and strict schema/record validation are required; do not silently mutate Run user_version or migrate ownership into old Runs.

Acquire OS task lock BEFORE durable queue/create and retain through slot wait, Running, terminal commit and synchronous guard cleanup. Queue/start/direct/managed/headless paths must all acquire or carry the same opaque guard; start must require the durable matching owner epoch, not just accept a free lock. On recovery acquire and retain that SAME stable task lock exclusively, reread the captured Run/Attempt + owner record in the recovery transaction and verify epoch/identity unchanged before committing Interrupted with its lifecycle event. Retain lock until commit completes, then release; a subsequent owner cannot begin concurrently. Never use TTL, PID absence, reused PID, old boot ID, or lock-path deletion as proof. Lock alone must not allow editing another task or resolving arbitrary renderer paths. Fixed lock order should be environment lease -> in-process task gate -> OS task lock -> SQLite transaction, used by mutations/reconciliation/queue; no reverse await while holding SQLite or std registry guards.

Crucial limitation: acquiring the parent owner's lock proves that cooperating parent holder released its handle, NOT that a shell child, detached tool, external provider request or remote subprocess stopped executing. ConfirmedGone cannot be asserted for arbitrary Running tasks merely from lock acquisition. A further supported execution-containment contract (Windows Job Object kill-on-close/process tree or equivalent, tracked external work and acknowledged shutdown) is necessary, otherwise preserve Unverifiable for possible surviving side effects. Interrupted is execution status, never automatic rerun/replay of tools or delivery, and unknown budget reservations remain retained.

Small implementation slices/files: new crates/agentz-task-state/src/execution_owner.rs for namespace/validated captured-owner CAS and Run transaction helpers in run.rs (queue/create owner transaction); new src-tauri/src/runtime/execution_owner.rs for platform OS guard/captured proof, exported runtime/mod.rs; durable_run.rs carries guard/epoch and ensures finish/Drop before unlock; chat.rs existing queue path and chat_turn.rs headless begin path must share this invariant. Recovery host service (new runtime module) retains verified scope/environment/task/OS guards and calls RecoveryStore, with recovery.rs transaction owner recheck. Cargo/lib exports/dependency/MSRV choice remain root-owned. Team/remote and side-effect containment are distinct later slices, not implicit acceptance.

Executable meaningful fixture plan: a Rust test executable launches its own exact ignored helper test in a separate process, communicates readiness via pipe, attempts the same canonical task lock and observes Busy; different task lock succeeds. Parent requests clean exit and acquires after wait; separately kills and waits for child then acquires, with bounded timeouts and RAII cleanup. Keep file on disk throughout, test canonical aliases/second independent handle, and demonstrate persistent owner row plus stale epoch rejection with actual SQLite transaction. Crash between queue/owner attachment must yield both or neither; terminal commit failure must not produce a false clean-finish assertion. On Windows wait for child handle exit before temp cleanup rather than deleting open lock files. These tests are feasible local fault fixtures, not yet run or proof of GUI/platform/remote behavior. Separate containment fixture must demonstrate surviving child cannot execute after owner loss before production ConfirmedGone is allowed.
