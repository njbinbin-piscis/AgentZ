# AZ-031 local secret-output candidate (2026-10-14)

The `app_control.get_settings` projection previously masked only string values under secret-looking keys. A non-string subtree under such a key could pass through unchanged, and provider-defined MCP `env`/`headers` names were not recognized. It now masks the whole subtree for secret-looking keys and for `env`, `headers`, `credentials` and `auth` containers. A unique synthetic marker in a nested API key, an arbitrary MCP environment key and a custom header was absent from the projected output; the scoped Rust test passed.

The host `get_settings` and `save_settings` response DTO omit stored global and named-provider API-key values. Existing empty update semantics retain these keys on a normal settings save. A Rust serialization fixture places one synthetic marker in every global API-key field and a named provider, then verifies the response contains none of it. This reduces renderer exposure for model API keys. The later host boundary change below rejects inline model-key writes.

The MCP settings response now retains environment and header names but masks their values. It also omits executable command, URL and argument values, exposing only configured flags; the form shows a hidden-value placeholder and accepts replacement input. Saving a masked environment key preserves its stored value; omitting that key removes it. Headers are preserved when the current form omits the whole map, since this form has no header editor. A named-server fixture verifies that a synthetic marker in command, URL, args, env and headers is absent from the serialized response and that the production save mapper restores the masked values. The model-facing `app_control.get_settings` now masks the entire MCP subtree, including nested arbitrary fields. The `app_control` settings diff shown to the model and stored in the audit log also masks the entire MCP subtree, while the separate rollback snapshot retains the original configuration. `cargo test --manifest-path src-tauri/Cargo.toml secret --lib --locked --offline` passed 10/10 on Windows, `npm run typecheck` passed, and the scoped diff passed `git diff --check`. Renaming a server does not carry its stored credentials, and clearing an existing command/URL/argument/header with an empty value still needs an explicit operation. Reference-only storage, other outlets and native GUI behavior remain unverified.

Historical audit-log entries may predate the diff mask. `app_changes::list` now masks secret-bearing paths and nested old/new values when returning them to UI or model callers, without changing the stored rollback snapshot. A synthetic historical MCP URL and named-provider API-key marker is absent from the projected diff; the scoped Rust test passed 1/1. Existing log files are not rewritten, so filesystem-level handling of old entries remains a separate review item.

The settings response now includes stable `model:<provider>` and `provider:<id>` references with existence booleans for global and named-provider API keys. Separate Tauri commands query, replace and delete these values; each returns only the reference and existence state. The replacement rejects empty and oversized values, and the existing encrypted `Settings::save` persists changes. The frontend IPC service exposes the operations for later UI migration. Three scoped Rust settings tests passed, including synthetic value non-echo and reference transitions; TypeScript noEmit passed. These are local API candidates, not a full vault contract: MCP secrets have no equivalent operations, concurrent settings writes were not exercised, and native command invocation was not run.

The model settings form now strips all global and named-provider API-key values from the general `save_settings` payload and sends staged replacements through `settings_secret_replace` after provider IDs are saved. Its placeholders use each reference's existence flag rather than global readiness, so a configured provider does not imply another provider's key exists. Global and named-provider keys can be staged for deletion, with the destructive operation sent only on the panel's Save; cancelling a named-provider edit discards its staged deletion. A replacement typed after staging runs after deletion. A synthetic frontend fixture confirms the old payload does not contain staged model-key markers; the focused Vitest test and TypeScript noEmit passed on Windows. This is a non-atomic migration: if a later secret operation fails, non-secret settings may already be saved; the form remains open for retry. MCP secret references are absent, and native GUI behavior was not exercised.

The host now rejects any nonempty global or named-provider API key in the general `save_settings` payload before loading or saving configuration. Existing stored keys are retained by empty fields, and dedicated reference operations remain the write/delete path. A scoped Rust fixture verifies both global and named inline submissions are rejected while a key-free settings payload is accepted; the four `secret_response_tests` passed on Windows with `--locked --offline`. This enforces the model-key portion of the reference contract at the host boundary. The save and subsequent secret operations are still separate writes, so atomicity and concurrent updates remain open.

MCP `command` and `url` now have `mcp:<server-name>:command` and `mcp:<server-name>:url` references. The existing query/replace/delete commands resolve them independently, including server names containing colons, and the settings response reports their presence. The form strips newly typed command/URL values from `save_settings`, then sends them through the separate replacement operation after server creation. The host rejects inline command/URL submissions on the general save path. A synthetic frontend fixture verifies the staged MCP values are absent from the general payload, and the five scoped Rust response/boundary tests passed on Windows with `--locked --offline`; frontend TypeScript noEmit and the focused Vitest test passed. The separate-write atomicity and native GUI journey are unverified.

MCP arguments now have an `mcp:<server-name>:args` reference. Its replacement value is a nonempty JSON string array, while deletion clears the array; malformed or empty arrays are rejected. The form sends newly typed arguments through the reference operation and the general save rejects inline arguments. A synthetic frontend fixture checks the argument marker is absent from the general payload; five scoped Rust settings tests, frontend TypeScript noEmit and focused Vitest passed on Windows. Existing hidden arguments are preserved on an empty general update. The form now stages explicit deletion of existing MCP command, URL or arguments for the panel's Save; a removed or renamed server's stale deletion is skipped. A later frontend TypeScript noEmit, focused Vitest and scoped diff check passed after this UI change. Native UI behavior remains unverified.

MCP environment and HTTP header entries now have key-specific references encoded as `mcp-env:["server","key"]` and `mcp-header:["server","key"]`. Existence reports whether the selected entry has a value; replacement creates/updates one entry and deletion removes it. The form strips values while retaining keys in the general settings payload, then submits newly typed values through replacement calls. The host rejects nonempty environment or header values in a general save. A synthetic frontend fixture covers both maps; six scoped Rust settings tests, focused Vitest, TypeScript noEmit and diff check passed on Windows. The tests exercise helpers and serialization, not native command invocation. The subsequent editor and explicit deletion candidate is described below; atomicity remains open.

The local form now provides an HTTP header editor alongside the environment editor. Both retain raw textarea drafts while a line is being typed, so an unfinished key is not erased by immediate map normalization. For existing servers, the form compares original and submitted map keys, then sends omitted keys through the dedicated per-key delete operation after saving metadata. The host preserves omitted entries during the general save, leaving deletion to that dedicated command. The deletion comparison checks own properties, including keys that collide with JavaScript object prototypes. This is a source-level candidate; native UI behavior and multi-operation atomicity remain unverified.

The form now submits metadata, secret deletions and replacements to `save_settings_with_secrets` as one batch. The host validates the general payload, applies all operations to one in-memory settings snapshot and calls the kernel's atomic settings save once. If a reference or replacement is invalid, no settings file write occurs. A scoped synthetic test confirmed an invalid later operation leaves the original file bytes intact and a successful batch persists both the model change and encrypted secret replacement. The desktop secret suite passed 7/7 on Windows with locked offline dependencies. This covers form-level write atomicity in one process; concurrent writers, native invocation and crash/recovery behavior remain unverified.

The four settings IPC write commands now share an in-process mutex around load-modify-save. `app_control` settings writes, instruction appends and settings rollback use the same guard; the append operation reads and writes while holding it. This serializes the known desktop settings write surfaces within one process. The desktop settings suite passed 7/7, app_changes suite 4/4 and app_control projection test 1/1 after this change. Cross-process writers and native concurrent journeys remain unverified.

The kernel settings store was found to serialize MCP command, URL, arguments, environment values and headers as plaintext despite masking them in UI responses. Settings secret format v2 now encrypts each nonempty MCP value before the same-directory atomic file replacement and decrypts it on load. Format v1 and untagged files retain their historical plaintext MCP interpretation so they can be loaded and migrated on the next successful save; v2 fails closed if an MCP ciphertext cannot be decrypted. A synthetic v1-to-v2 fixture confirms all five markers disappear from the saved JSON, values round-trip, and a corrupted v2 environment ciphertext is rejected. The kernel settings suite passed 11/11 and the desktop secret response suite passed 6/6 on Windows with locked offline dependencies; scoped rustfmt and diff checks passed. Existing v1 files and backups are not rewritten until saved, so on-disk migration and rollback handling still need release review.

New `app_control` rollback snapshots now encrypt their full before-image with the config directory's protected secret key. The snapshot envelope contains a change ID bound inside the ciphertext; rollback rejects an ID mismatch and still reads historical plaintext snapshots for compatibility. A synthetic MCP secret marker was absent from the encoded snapshot, decrypt/identity checks passed, and the existing record/list fixture passed on Windows. This does not rewrite existing plaintext snapshots, prove snapshot write crash recovery, or validate a real rollback journey.

The settings rollback branch now calls a shared restoration helper. A filesystem fixture feeds that helper a historical plaintext snapshot containing an MCP command marker, verifies a malformed non-object snapshot leaves the current file untouched, and confirms the restored value loads while the resulting format-v2 JSON contains no plaintext marker. The audit secret suite passed 3/3 on Windows with locked offline dependencies. This exercises the rollback implementation below the Tauri command, not the native UI, full audit history, or a crash-injected rollback.
