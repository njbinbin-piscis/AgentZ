# AZ-020 chat turn wiring: independent read-only review

Reviewed 2026-10-08 in the shared working tree. No product files were changed, no Cargo/TypeScript build, GUI, model call or external action was started. Parent-owned host build 91538 and TypeScript check 96157 were in flight; their results are not asserted here.

## Registration-blocking finding: legacy development environment cache writes

P1: `commands/chat_turn.rs` publishes the durable recovered projection, but later calls `commands/devenv.rs::context_for_turn` with the same plan cache. That function scans the environment and, on its first qualifying session, directly pushes a pending development-environment todo into the kernel cache and emits a legacy plan event. It does not write `plans.db`. The following retained-todo prompt and harness therefore consume a different plan than the validated durable recovery snapshot.

Reproduction boundary: start a local interactive agent turn in a project whose environment scan produces a non-dismissed missing requirement, with a newly recovered empty or existing durable plan. The first environment hint inserts a cache-only todo. A subsequent durable `plan_todo` operation merges from its authoritative durable projection, losing the implicit cache-only item; restart likewise cannot recover it. The completion guard may also see pending cache-only work that the durable store never contained. This is established from source paths, not a GUI/model reproduction.

The registry separately captures the original shared cache in `DevEnvTool` before the durable/unsupported cache selection. `tools/devenv.rs` resolve/dismiss paths call `clear_todo`, which removes the implicit item and emits a legacy plan update without a durable operation. Switching only `context_for_turn` to a pure hint is insufficient for already retained development-environment items. Unsupported/background turns use a disposable harness cache but their previously constructed development-environment tool can still retain the original shared cache. Recommended bounded fix: use pure environment hints and detach development-environment tool writes/events from the durable projection; an actual durable edit must use the durable service and explicit revision semantics. Do not silently clear authoritative plans.

Both paths were immediately reported to the parent. This review does not waive their fix or the original acceptance gate.

## Identity and lifetime paths checked

- Host Run identity is taken from the queued Run or generated by the host; early binding explicitly retains its attempt ID. `start_bound` or `begin_bound` commits Running before `ActiveAttemptGuard::acquire`.
- `durable_run` is declared before the optional plan guard. On an early `?` return after successful activation, Rust reverse local drop order revokes the capability before the Run guard attempts Interrupted. Constructor/publication failure drops the local activation guard before the earlier Run guard. The registry may retain tool capabilities, but revocation applies to their shared active state.
- The success path explicitly drops the plan guard before `ManagedRun::finish`. The capability is therefore revoked before terminal Run state persistence. Synchronous writes already linearized before Drop may finish; no retroactive cancellation guarantee is claimed.
- ApprovalHooks is constructed with the same host run/attempt and its freshly resolved Binding must exactly equal early Binding. The tool also checks fresh environment against its captured identity. Environment access leases in both known shared-runner callers (`chat_send`, heartbeat dispatch) are acquired before their state work and retained across the awaited whole turn.
- Current call graph contains exactly two `run_agentz_turn` callers: chat passes `Some(permission_responses)`, heartbeat passes `None`. Thus `confirmation_responses.is_some()` currently distinguishes these callers, but it is an implicit convention rather than a typed interactive capability. New callers must not infer authorization from an arbitrary response-map allocation.
- Durable replacement is conditional on an already present `plan_todo`, local scope and the interactive convention. The original restricted registry is not broadened when the tool is absent. Unsupported/background turns unregister `plan_todo`; the omission is explicit and no legacy plan-write fallback is installed. Remote turn handling already requires a local canonical root earlier in this runner, so this read does not establish functioning remote durable planning.
- `clear_plan=true` is rejected at the beginning of `chat_send`, before environment lease/queue/Run side effects. Default/false preserve intent. Heartbeat now passes false; the shared runner also rejects true. No actual new-objective replacement command is asserted by this change.

## Validation limits and fingerprints

The prior tool/storage fixtures assess primitive recovery, guarded writes and no-write failure cases. They do not reproduce this full host registry, development-environment hint, termination and model/harness flow. Suggested meaningful new check: recovered durable snapshot remains the exact prompt/cache source despite environment hints; development-environment resolve/dismiss cannot mutate it through legacy cache calls; and a retained tool fails after actual host terminal/early-error revocation.
