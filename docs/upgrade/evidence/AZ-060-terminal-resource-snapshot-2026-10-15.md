# AZ-060 owned PTY resource snapshot candidate

The desktop host now exposes `ide_terminal_resource_snapshot`: registered PTY sessions and, on Windows, the sum of active processes in their owned Jobs. The snapshot omits terminal IDs and output. Job query failure returns an unknown process total (`null`) with a failure count, so a failed census cannot masquerade as zero. On non-Windows the process total is explicitly unavailable. It also exposes a local filesystem-watcher count, an extension-host snapshot containing child presence, connection state, pending RPC requests and remote-watch registrations, and a graph-index snapshot of queued/worker projects, pending files, cached status and retiring projects. No project or extension identifiers are returned.

The CodeZ development surface exposes `window.__agentz_codez_resource_snapshot()` while mounted. It reads Monaco's actual global model count, tracked CodeZ model count and live tracked model count, a balance of CodeZ chat/browser/file-change/terminal output listeners, then requests the native PTY, watcher, extension-host and graph-index snapshots. A failed native call is represented by `null`, not zero. The hook is removed on pane unmount. Listener registration counts only after the event API returns an unlisten function; cleanup is idempotent and also handles registration resolving after unmount. The tracked listener number is deliberately a subset of all application listeners, and the host watcher count excludes remote watchers. These counts can be sampled beside the AZ-057 process sampler during a future desktop soak. The two-shell late duplicate registration fixture checks a live owned session, verifies that rejection leaves the first session counted and reaps the second, and checks zero after closing the first. A second fixture synchronizes two real PTY shells before they contend for the same host registry mutex, confirms exactly one is retained, the rejected shell is reaped, and final close leaves zero sessions/processes. This exercises the shared registration path, not actual concurrent Tauri command invocation. The snapshot commands and development hook have not been exercised through a native Tauri window.

CodeZ now sequences filesystem-watcher release after a successful start. Previously an unmount could send stop before an in-flight start had registered its watcher and leave it running. A controlled delayed-start fixture checks exactly one stop after start settles; a failed-start fixture checks that cleanup does not claim or stop a resource never acquired. The local host watcher registry now counts successful start owners for each project. An intermediate stop leaves the watcher and callbacks active; the final stop releases them and clears graph-index cache. A native registry fixture creates a real OS watcher and verifies both releases. Remote watcher registrations have a separate lifecycle and are not covered by this local owner count.

On local watcher close, graph-index state now drops queued work and volatile cached phase/result/error entries for that project. An already running graph build may finish; its cached status is discarded when it exits. A new enqueue while it runs cancels retirement and remains eligible for another pass. The local watcher now owns an activity flag that is cleared before its callbacks and index worker are released. Late rebuild and incremental callbacks check that flag while holding the graph queue lock, so they cannot recreate the retired queue after close. Controlled fixtures cover idle cache release, retirement followed by worker completion, late rebuild/incremental requests after close, the actual queued worker thread exiting after its project is forgotten, and an in-progress worker blocked inside a controlled build while the project closes. The last fixture confirms the failed build result is discarded and worker/cache state is released. A synthetic Rust project fixture now runs the real graph generator, closes the project after generation, and verifies the worker discards phase/result/error status when it exits. This does not establish behavior for a large real repository or a close during the generator's own work. A concurrent incremental callback can still mark a file pending on disk just before close, but cannot retain a volatile queue afterward.
