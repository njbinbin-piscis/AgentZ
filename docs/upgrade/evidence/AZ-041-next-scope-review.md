# AZ041 editor conflict scope independent review

2026-10-10. Read-only inspection during frozen offline/locked NSIS build. No source, ledger, previous evidence or build changes; no tests/GUI/OS race validation run.

All three reported correctness risks are confirmed in current CodeZ index.tsx: scheduleTabReload deleted branch at 494 removes matching tab regardless of isDirty; modified dirty branch clears isDirty after confirmation before the debounced read succeeds; its completion maps by relative path without project generation/local revision. reloadTabFromDisk also applies by path and silently ignores failures. saveFile at 748 captures content/project then clears dirty by path after write, even if the user edited or changed project while awaiting. These can lose recoverable local content or falsely classify newer content clean. Existing navigation dirty checks do not fix a watcher removing/cleaning that state first.

Minimum safely deliverable frontend protection: maintain scoped tab identity, project generation and monotonic local revision; capture them for each read/save and settle only exact matching ownership/revision. Retain dirty deleted tabs with explicit deleted status; watcher is invalidation only. Failed reads/writes must retain buffer and dirty state with visible error. Remove pre-read clean marking. Older successful saves may acknowledge only the captured revision, leaving later edits dirty. Same-content equality alone is insufficient for project/tab ABA or editor revision tracking. Pure fixtures should exercise dirty deletion, read failure after consent, typing during pending reload/save, same-path project switch, close/reopen tab and out-of-order responses.

The proposed retained-base/conflict reducer and explicit comparison/Keep local/manual merge are reasonable follow-up boundaries. A restored dirty buffer without a known disk base must label base Unknown; no three-way success can be claimed. Applying a draft affects only local state and remains dirty. Explicit replacement must be tied to both captured local and observed disk revisions. Retaining buffers in memory is not durable restart recovery; dedicated versioned persistence and actual restart tests remain separate acceptance.

Frontend generation guards do not make ide_write_file atomic or prevent external/Agent writes between last observation and write. Blocking known unresolved conflicts can reduce loss but leaves unobserved races. Expected hash/identity checked-write must be host/scope-authorized, use actual same-handle/exclusive creation semantics and account for external writers/rename/delete and all other write actors. Existing readonly task scope cannot mint this write authority. App-only mutex or read-then-write comparison cannot establish full no-overwrite acceptance.

Release assessment: these confirmed local-buffer-loss/false-clean paths should block promotion to a stable IDE product until at least preservation/revision/error guards are implemented and verified. They do not require aborting or mutating the currently frozen local candidate build; the package can remain explicitly an unaccepted testing candidate with AZ041 outstanding. No claim of stable-ready, fully safe concurrent editing or rollback follows from candidate packaging. Full checked-write acceptance and native Monaco/external-process/restore scenarios must remain separately gated. This is an engineering release-risk recommendation, not automatic ledger/Gate status change or a request to publish.
