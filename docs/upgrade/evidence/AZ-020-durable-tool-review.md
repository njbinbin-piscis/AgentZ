# AZ-020 durable plan tool read-only review

2026-10-07. Reviewed `tools/durable_plan_todo.rs`, the durable plan service's six existing fixtures, plan storage validation and relevant approval/name/cancellation interfaces. The primary agent's targeted build (66775) was still in progress at assignment time; this reviewer did not start Cargo or claim its result. Only this evidence file was written. The tool explicitly remains an **unregistered draft**.

## Identity, names and cancellation

The captured Binding is host-supplied and immutable. Each call checks task/session equality, exact Arc identity of the cancellation flag, canonical workspace equality, fresh project/environment/Git binding, then restores only the captured Attempt ID before comparing the entire Binding. This correctly preserves a distinct host Attempt rather than accepting resolve_binding's compatibility default attempt_id=run_id. A fresh environment result is not used to select a new Attempt.

Tool name is exactly `plan_todo`; input schema is delegated to the existing kernel PlanTodoTool, and the approval hook recognizes that same internal tool name. ToolContext cancellation is the same AtomicBool pointer, so the later Acquire check and ctx.is_cancelled do not refer to unrelated stop slots. This is good identity consistency, not proof that the Run remains active.

Lock order is tool service state then disposable plan cache. Binding resolution awaits Git checks while both locks are held; no SQLite transaction spans that await. The tool's service lock is private and no reverse cache→service lock path was found in the reviewed files. Calls waiting for either lock subsequently check cancellation before writing. Holding the cache while Git is slow may delay UI/harness reads but is not itself a demonstrated deadlock.

## Two registration-blocking integration requirements

1. **Active Attempt lease is not enforced by this draft.** Constructor/call verify binding shape and fresh environment but never establish or check an active Run/Attempt. The owned tool tests intentionally do not create a Run record. If a host retains the tool and identical context after finishing that Run, another call can still write the plan while cancel remains false. Registration must retain an environment read lease through the whole turn and a trusted Run/Attempt activation token revoked on completion, early exit and replacement. A global environment read lease alone prevents cleanup but does not attest this specific Attempt is active. If live state is checked via RunStore, avoid a check/commit gap by specifying its synchronization with the host lease; do not treat renderer IDs or a previously issued Binding as liveness authorization. Test calls after finish and old-attempt replacement as no-write/no-event failures before activating the tool.
2. **Recovered projection needs registration-time publication.** DurablePlanSession::recover stores the recovered projection internally, but the constructor does not hydrate the shared kernel PlanStore. Replacing the kernel tool without an explicit host restore step can leave continuation/harness/UI seeing an empty or stale disposable plan despite durable state. Host registration should publish the recovered projection under the same session before the loop reads it, with empty/history/replaced behavior specified. Add a reopen/new-turn test asserting the cache and initial visible plan are recovered without requiring an extra plan_todo write. Starting a new turn must not clear durable state to address this issue.

The current chat_send holds an environment access lease before queueing through its turn, but background/delegated routes and lifetime of a retained tool must be accounted for explicitly. This document does not modify or assert full coverage of those routes.

## Commit, cache and event publication boundaries

Storage success advances the service revision/projection. Cache lock is already acquired, and there is no await after the synchronous database commit before cache insertion and emit. Storage failure therefore cannot publish a new disposable cache/event; the insert-trigger fixture covers that case. Cancellation after the last check, including during SQLite lock waiting, is a race with the accepted write; specify that boundary rather than promising all Stop-before-commit signals prevent a commit.

`serde_json::to_value(PlanUpdate)` is after commit and before cache update. Current PlanUpdate contains string-based todo fields, so no ordinary serialization failure was identified. A future fallible event shape or custom serializer would create committed-plan/stale-cache failure and should be serialized from the proposed projection before commit or recovered explicitly; it is not a present reproducible failure.

EventSink emit returns no delivery acknowledgement. Even with commit→cache→emit order, a process crash or sink failure can leave a committed plan without a delivered event. PlanUpdate emission is best-effort UI notification, not an atomic durable event/outbox. On reopen the database must remain authoritative; AZ-018 streaming integration is a separate package. No automatic replay of side effects is implied by restoring a plan.

## Test assessment and unverified scope

The tool has three fixtures: distinct Attempt with matching kernel schema and committed cache/event; wrong task, different cancel Arc and cancelled call with no effects; SQLite insert failure with no cache/event/captured revision. Service fixtures cover actual reopen/revision stale handling, failed writes, binding mismatch, status conversion, continuation and closed-plan rejection. Existing checks are relevant to storage/projection semantics, but do not attest an actual active lease, registration-time recovery, background integration, cancel during a blocked database transaction, process death after commit, or real renderer/LLM interaction.

Recommended next targeted checks are active-Run lifetime rejection and registration-time cache restore after restart. The main agent owns implementation, combined tests and ledger updates. AZ-020 remains preparing until its original acceptance is met; this review neither registers the draft tool nor waives any gate.

## Active capability and recovery publication follow-up

Read-only review while the primary agent's unique targeted host test build 37290 was running. No additional build was started and its eventual result is not asserted here.

The new non-cloneable `ActiveAttemptGuard` owns a cloneable tool capability containing fixed Binding plus active status. Drop takes the same synchronous mutex used by write/publication and revokes active status, recovering poisoned state only to revoke. Calls reject a poisoned capability. All awaits precede `lock_active`; the guard is held across synchronous state write, projection cache insertion and emit, with no await under that lock. Thus a revocation that obtains the lock first prevents mutation/publication; a write that obtains it first can complete before revocation returns. This is a linearization boundary, not retroactive cancellation. SQLite lock waiting can delay Drop until the bounded synchronous operation returns; it does not cause a discovered lock-order cycle in this draft.

`publish_recovered_projection` now takes service/cache locks, fresh-checks the captured binding and restored Attempt identity, checks active capability and cancellation, and rereads current plan identity/revision before using the original recovered projection. Stale recovery fails instead of overwriting the prompt cache. Publication does not write the plan or increment revision, and uses the same cache/event order. These changes address both earlier draft integration gaps **at the tool primitive level**. Exact ctx cancellation Arc checks remain enforced for tool calls; recovery publication uses the already captured tool cancel Arc rather than accepting a replacement ctx.

No new registration P1 was found in this read. Remaining host requirements are explicit: `ActiveAttemptGuard::acquire` validates Binding shape only, so the caller must create it only after a real host Run/Attempt lease is active, retain the environment lease, and revoke the capability on every terminal/early-exit/replacement path before final lifecycle publication. Two independently acquired guards for the same Binding do not mutually revoke; avoid issuing duplicate activation capabilities. Do not register or retain this tool beyond that host-owned lifetime without the revocation path.

The public `recovered_projection` accessor still returns an unchecked cached projection, so prompt initialization must consume the validated `publish_recovered_projection` result rather than that raw accessor. It is not a replacement authorization check. The added tool fixtures establish revoked/wrong-capability rejection and cache restoration primitives, but do not yet establish all real host terminal paths, environment lease integration, or a distinct new Run/Attempt continuation. Best-effort event delivery and the external-Git fresh-check race remain as described above. The draft is still unregistered in the reviewed source.
