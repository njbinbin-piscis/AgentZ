# AZ020 explicit chat plan command wiring design

Read-only design; no IPC registration, product edits, Cargo, model or GUI run. plan_intent targeted build48342 was in flight when assigned; its outcome is not claimed here. Post-candidate work is not included in0.9.7.

## Request and response contract

Proposed `commands/chat_plan.rs`: `chat_plan_get` accepts `{ projectDir, sessionId, workspaceDir?, requireTaskEnvironment? }`; `chat_plan_apply` accepts the same scope plus `{ expected: { id, revision }, intent: { kind: "replace", objective } | { kind: "cancel" } }`. Deserialize with deny_unknown_fields on typed DTOs, validate nonempty IDs and positive revision, bound objective to existing PlanStore text limit, and reject remote scope until supported. No renderer runId/attemptId/bindingVersion/capability or opaque authorization booleans are accepted.

Response is PlanQuery `{ binding, current }` with current full persisted Plan including closed status/items; successful mutation returns that same fresh scope and committed Plan. Do not return only PlanUpdate items. Structured errors should distinguish `identity`, `environment_changed`, `busy` (active/queued Run), `stale_plan` (expected ID/revision), `storage`, `unsupported_scope`; stale/busy are visible messages with refresh/stop guidance, not automatic retries.

## Actual existing identity evidence and gaps

`data_scope::require_project_dir` only checks supplied directory exists, then open_project_kernel_state can initialize its .agentz database. **It is not a trusted open-project registry or authorization check.** AppState has watchers, cancellation flags and plan cache but no audited project/session authorization registry. workspace.rs persists a renderer-supplied projectDir snapshot, which is not a stronger ownership boundary. default capability names only main window; this file alone does not establish per-command custom invoke authorization or project provenance. No new command should treat any existing directory as permission to initialize/modify plan state.

For a managed task, agentz_task_state::load and agent_task::validate_task_environment verify registered record and live worktree/Git identity; resolve_task_workspace enforces requested root equality when a record exists. With require_binding=false and no record it accepts a supplied workspace, so direct-session handling must additionally require an **existing project-local session row**, not create/ensure a new session from this command. Read the existing session's workspace_root/source and match canonical requested workspace to the established direct project/session scope. Missing session is an identity error; user must first create/open the task via existing host flow. Managed tasks should also require the corresponding known session and supported CodeZ/WorkZ source. Existing session::validate_session_continuation provides source separation, not general project permission.

Before IPC activation, root must select and implement a real host-owned project/session scope verifier (or explicitly constrain new commands to a verified current main-window project handle issued by host). No such verifier was found in the reviewed files. This is a concrete authorization gap, not fixed by canonicalization, session-ID shape or a filesystem exists test.

## Fresh environment identity without fake Run authority

Plan query/intent requires PlanBinding only. Extract/share the project/workspace/registered-record/direct-Git fingerprint portion of approval::resolve_binding into a plan/environment resolver; preserve the exact binding-version algorithm so running plans remain compatible. It must perform trusted scope validation first and compute fresh binding each operation. Do not create fake Run/Attempt IDs, instantiate ApprovalHooks, mint ActiveAttemptGuard or claim tool execution rights for a plan query/Cancel. The plan service is metadata authority only.

## Gate / active Run / CAS order

After trusted canonical scope resolution, retain environment execution lease (excludes cleanup), then acquire the **same per-task mutation gate** used by every Run queue/start path, keyed by canonical project+task. Under that gate freshly resolve environment binding, read RunStore.has_active_task (queued/running/cancelling count as busy), then invoke plan_intent.apply with the gate adapter held until synchronous CAS completes. Never release between idle check and write, and do not use chat_cancel/task_cancel emptiness as authority. Root must coordinate actual API/lock ordering with the two owners implementing gate/active query. These are in-process exclusions only; do not claim cross-process exclusion or Run/Plan cross-database atomicity.

Query may use the same gate for a coherent identity/head snapshot but does not require idle; active plans can be displayed. Replace/Cancel reject active/queued Runs and do not stop them. If a stopped Run guard hasn't reached terminal persisted state yet, remain busy. SQLite new schema/corruption/error fail closed without replacing with an empty plan.

## Cache and UI consistency

After mutation commit, publish current-plan projection into disposable state while task gate is retained (closed Cancel becomes empty runtime projection; authoritative DTO retains historical cancelled items). No await/side-effect retry may reinterpret failed publication as failed commit. On publication error return specific committed ID/revision plus refresh requirement; never reapply the intent. UI uses full DTO and filters project/task/environment/request generation; late task-A response must not overwrite task-B. Prefer an explicit dedicated authoritative plan event; legacy PlanUpdate cannot communicate plan identity/status/revision. Next turn recovers database through its existing DurablePlanTodoTool single-recovery flow before prompt, so a lost UI event does not lose the plan.

Minimal ownership packages: commands/chat_plan.rs for DTO/verifier/resolver/gate/service adapter; commands/mod.rs and lib.rs exports/registration by root; shared environment resolver and real gate integration as separately reviewed changes. No registration before trusted scope verification and shared queue gate coverage are tested. Required fixtures: nonexistent/other-project/direct unknown session refusal, registered worktree mismatch, active/queued busy, queue-vs-intent serialization, stale CAS, storage rollback, committed-but-notified failure refresh, closed query, A/B late result isolation. Actual desktop/model acceptance remains separate.

## Follow-up: smallest practical host project scope

Read-only search found no backend recent-project/open-project registry. `src/App.tsx` owns current projectDir in React state; pickFolder calls services/tauri/index.ts::openFolderDialog (plugin-dialog JavaScript open), then switchProject. Workspace hot-exit data is written by workspace_save from renderer snapshot. WorkZ also selects task work directories via that folder picker. Remote open paths dispatch `agentz:open-project` CustomEvent. These are useful UI open lifecycle sites, but their strings are not already host-issued project authority.

Extension webviews are iframe srcDoc with opaque origin (`sandbox="allow-scripts"`, no allow-same-origin); WebviewHost checks exact source plus origin="null" and sends only bounded messages to extensionService. MainThreadCommands builtins support a small list (setContext, vscode.open/revealLine/save) and have no project-scope mint or chat-plan command. Rust source search found no WebviewWindowBuilder/WebviewBuilder path creating an additional privileged extension window; Tauri config/default capability uses main. These observations support **constraining the new flow**, but do not prove all custom commands are automatically ACL-denied to subframes. Explicit WebviewWindow label/origin restrictions and absence of a forwarded mint command remain required tests.

Minimal implementation option (no extra confirmation): add host-owned ProjectScopeRegistry to AppState. At the existing main GUI project-open lifecycle, obtain an opaque random handle from a main-window-only scope-open operation; canonical root is stored in host registry with window label and generation. Prefer moving the existing folder-selection action to a host command that receives its selected path directly from the native picker, then registers it and returns `{ handle, canonicalProject }`, retaining current UI UX. An arbitrary renderer `register(path)` operation establishes only trusted-main-renderer scope, not proof of native-picker selection; explicitly document that trust boundary if used for restored/open-existing paths. Do not let file-list/model tools or extension command bridge call scope-open, nor use agent_task/load-directory calls to mint handles.

For hot-exit restore, host can issue a new scope for its existing workspace snapshot under main-window restore flow after canonical validation; stale handle from previous process is invalid. Since that snapshot was renderer-written, it is restore metadata rather than provenance/ownership proof. Bound exposure to this main-window scope and existing project-local session. WorkZ's separate per-task folders require host scoped handles issued through the same lifecycle; a global single-current-directory assertion would incorrectly reject legitimate multi-project tasks. Registry can retain an explicit finite set of opened scopes per window instead, revoking on close/switch or retaining only still-open WorkZ tasks.

New chat_plan requests should use `{ projectScope, sessionId, workspaceDir?, requireTaskEnvironment?, ... }` instead of arbitrary projectDir. Lookup rejects unknown/revoked/window-mismatched/generation-stale handles before opening any database; derive project root from registry and require existing session row/source. Managed workspace resolution still uses registered environment/Git checks. Direct sessions match stored workspace or scope project root; no directory-only session creation. Handle is stored in trusted renderer state, never prompts/model context, extension postMessage payload, URL or logs. Window-label check alone is not a token replacement: a compromised trusted main renderer can still mint/use its authority; scope handles bound paths and stop unregistered arbitrary-path command use rather than claiming protection against that renderer compromise.

A smaller interim **unregistered** command service can accept a host-internal VerifiedProjectScope value supplied by chat/open lifecycle and test scope/session validation now, while registry/native-picker IPC connection proceeds in an isolated package. This is reversible engineering work and needs no new user approval flow. Activation remains dependent on implementing the real scope source, not waiting for hypothetical stronger ownership assurances. Required scope fixtures are unknown/mismatch/revoked handle no DB creation, valid picker/restored scope plus existing session succeeds, extension bridge cannot mint/forward scope, and WorkZ multiple opened project scopes retain task isolation.
